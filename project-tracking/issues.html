ISS-001 VERIFIED Unrelated paths merged into same compound path
Two completely separate duct runs (L-shape and U-shape) 22pt apart were being incorrectly merged into one compound path.
Root Cause & Fix (line ~9924)
Root Cause:

T_JUNCTION_DIST was set to 25pt, way too high. Any path endpoint within 25pt of another path's segment was considered a T-junction connection, even when paths were unrelated.

Fix Applied:
  • Reduced T_JUNCTION_DIST from 25pt to 3pt (line ~9924)
  • Added skip for T-junctions at exactly 4.25pt (carve-out gap distance)
  • Added self-intersection handling to skip blocking when otherPath = pathToCarve
Lesson Learned:

Check spatial thresholds FIRST when debugging connection/compounding issues!

ISS-002 PENDING Subsequent runs extremely slow after processing large ductwork
First run on massive ductwork was fast. Selecting just 2 lines afterwards and hitting Process Ductwork caused window lockup and took a very long time. 247 components updated taking 11+ seconds.
Root Cause & Fix (lines 17981-17982, 19229-19230, 18679-18703)
Root Cause #1 (PRIMARY):

Line 17981 cleared doc.selection BEFORE STEP 7 component placement. This caused STEP 7's proximity filter (line 18909) to be disabled because it couldn't re-collect selected paths (lines 18050-18062). Result: processed ALL 247 components document-wide instead of just those near the selection.

Root Cause #2 (SECONDARY):

Line 18681 blindly updated targetItem.file for every existing item (11 seconds for 247 items at ~45ms each) even when the file link was already correct.

Fix Applied:
  • PRIMARY FIX (lines 17981-17982, 19229-19230): Moved doc.selection = null; from BEFORE STEP 7 to AFTER STEP 7. This preserves selection during component placement so proximity filter works correctly.
  • SECONDARY FIX (lines 18679-18703): Added check to skip file link updates if targetItem.file.fsName === file.fsName (already correct).
Expected Result:

Instead of processing 247 components document-wide (11+ seconds), now processes only ~5-15 components near selection (under 1 second).

ISS-003 VERIFIED Units disappearing in unrelated locations
Processing a selection caused units in totally different areas (not selected) to disappear. Unit at 300.08,1183.44 was being deleted even though selection was at Y=1014-1114 (69pt away).
Root Cause & Fix (lines 9164-9191, 14957, 18251)
Root Cause:

placeComponentAtAnchorPoints_local() in STEP 7 (line 18359) was checking ALL docParam.placedItems against ALL ignored anchors. No bounds checking whatsoever - if any unit anywhere in document was within 4pt of any ignored marker anywhere, it was deleted.

Why bounds calculation failed: By the time STEP 7 ran, selectedPaths was empty (paths had been processed into compound paths), so bounds calculation returned nothing.

Fix Applied:
  • Calculate selection bounds EARLY at start (lines 9164-9191) - right after collecting paths, before any processing
  • Store bounds globally in $.global.MDUX_SELECTION_BOUNDS
  • STEP 2 uses global bounds (line 14957)
  • STEP 7 uses global bounds (line 18251)
  • Both removeConflictingArtAndAnchors() and placeComponentAtAnchorPoints_local() check bounds with 50pt buffer
Safety Improvement:

Only items within 50pt of selection bounds are checked for conflicts.

ISS-004 PENDING Register placed at Unit anchor point
Two blue ductwork endpoints close together should have ONE unit. Instead, script places a register at one endpoint. Using ignore marker to prevent register also deletes the unit on subsequent runs.
Root Cause & Fix (lines 18311-18334, 18341, 18658-18674)
Root Cause:

No priority system for component placement. When multiple component types have anchor points at the same location, all types were placed without checking for conflicts. Ignore markers affected ALL component types equally (including Units).

Expected behavior: Units should take priority over registers at shared anchor points.

Fix Applied:
  • Collect all existing Unit positions BEFORE processing any components (lines 18311-18334)
  • Pass Unit positions to placeComponentAtAnchorPoints_local() (line 18337)
  • For register types, check if Unit exists within 10pt of anchor before placement (lines 18658-18674)
  • Skip register placement if Unit found at that location
Result:

Units now take priority over registers at shared anchor points.

ISS-005 PENDING Random Illustrator freezes requiring task manager kill
Extension causes Illustrator to randomly freeze completely, even when not actively being used. Also freezes Python server window and Chrome. No warning, no ability to save work. Only fix is End Task in task manager.
Root Cause & Fix (js/panel.js 1515-1548, jsx/magic-final.jsx 198-243)
Root Cause #1 (Panel polling):

Polling loop at js/panel.js:1518-1523 calling evalScript() EVERY 2 SECONDS. When Illustrator's ExtendScript engine is busy or under load, these calls BLOCK the JavaScript thread indefinitely.

Root Cause #2 (Python bridge blocking):

Python Bridge wait loop using $.sleep() with 60 second timeout. When Python server crashes or hangs, Illustrator is FROZEN for up to 60 seconds.

Fix Applied:
  • FIX #1 - Panel Polling (js/panel.js lines 1515-1548): Implemented SMART POLLING with change detection. Fast check every 1 second (just selection count + typename), only expensive refresh if selection changed.
  • FIX #2 - Python Bridge Timeout (jsx/magic-final.jsx lines 198-243): Reduced timeout from 60s to 10s, added cancellation check inside wait loop, graceful fallback to ExtendScript.
  • FIX #3 - Debug Logging: Removed excessive evalScript('MDUX_debugLog(...)') calls from refresh functions.

ISS-006 PENDING Blue ductwork path completely erased during processing
One of the 4 blue ductwork paths in the selection was completely deleted during processing, leaving only 1 point (invisible/invalid path).
Root Cause & Fix (lines 13474-13491)
Root Cause:

FR-003 was DELETING anchors near intersections and ADDING new vertices. When you delete an anchor, any OTHER path that has an endpoint connecting to it loses the connection, creating a gap.

What happened: FR-003 found anchor [1205.30,1349.24] which was 0.13pt from intersection. It deleted this anchor and added a vertex at [1205.21,1349.15]. But another path had an endpoint connected to [1205.30,1349.24]. After deletion, that endpoint was disconnected.

Key Insight:

When an anchor is part of a line and near an intersection, you must SNAP it to the intersection, not delete/recreate. Snapping preserves all connections to other paths.

Fix Applied:

Changed from DELETE+ADD to SNAP:

snapPts[anchorIdx].anchor = [intPt[0], intPt[1]];
  • Before: Delete anchor at [1205.30,1349.24], add vertex at [1205.21,1349.15] - breaks connection
  • After: Move anchor from [1205.30,1349.24] to [1205.21,1349.15] - preserves connection
Result:

FR-003 now SNAPS misaligned anchors to exact intersection points. All path connections are preserved. No gaps.
